# 프롬프트 1 — 지표·통계 엔진 감사

**첨부할 파일:** `lib/cycle/signals.ts`, `lib/cycle/ta.ts`, `lib/cycle/evaluate.ts`, `lib/cycle/regime.ts`

```
너는 퀀트 리서치 코드 리뷰어다. 첨부한 TypeScript 파일 4개는 "과거 상승장
시작점을 어떤 기술적 지표가 잘 잡았는가"를 채점하는 백테스트 엔진이다.

signals.ts  — 30개 지표를 켜짐/꺼짐 상태 배열로 정의
ta.ts       — RSI/MACD/볼린저/ADX/스토캐스틱/CCI/일목 구현
regime.ts   — 지그재그로 고점·바닥(=상승장 시작일) 라벨링
evaluate.ts — 적중률·리드타임·정확도·lift·p값 계산

아래 4단계로 감사하라. 추측하지 말고 반드시 코드의 줄 번호를 인용하라.
문제가 없으면 "이상 없음"이라고 분명히 말하라. 없는 문제를 지어내지 마라.

[1단계] ta.ts의 지표 구현이 교과서 정의와 일치하는가
지표별로 하나씩 확인하라:
- RSI: Wilder 평활(1/period)을 쓰는가, 단순평균이 아닌가. 첫 값 시드가 맞는가.
- MACD: EMA 시드가 SMA인가. 시그널선을 MACD가 정의된 구간부터만 돌리는데
  이 방식이 표준 차트(TradingView)와 값이 달라지는가.
- 볼린저: 표준편차 분모가 n인가 n-1인가. 어느 쪽이 관례인가.
- ADX/DI: Wilder의 TR·+DM·-DM 정의와 평활이 정확한가. DM이 동시에 양수일 때
  처리가 맞는가. ADX가 DX의 평활인가.
- 스토캐스틱: %K 기간, %D가 %K의 SMA 3인가. Fast/Slow 중 어느 쪽인가.
- CCI: 전형가격(H+L+C)/3과 평균절대편차 0.015 상수를 쓰는가.
- 일목: 전환/기준/선행A/선행B의 기간과 26봉 앞 시프트가 맞는가.
  ★ 특히 선행스팬을 미래로 시프트할 때 look-ahead(미래 정보 참조)가
    생기지 않는지 반드시 확인하라.
- SMA/EMA: 워밍업 구간을 null로 정확히 막는가. off-by-one이 있는가.

[2단계] signals.ts의 지표 정의가 그 이름값을 하는가
30개 각각에 대해:
- 조건식이 라벨과 실제로 일치하는가. (예: "골든크로스"라면서 교차가 아니라
  단순 대소비교(gt)를 쓰는 게 여러 개 있다. 이게 의도된 설계인지,
  어떤 통계적 결과 차이를 만드는지 설명하라.)
- 미래 정보를 쓰는 지표가 하나라도 있는가. 주봉/월봉을 일봉에 투영할 때
  (fromPeriod/projectToDaily) 아직 안 끝난 주/월의 값이 새어 들어가는가.
- 서로 거의 같은 지표가 몇 쌍이나 있는가. (예: 200일선 위 / 50-200
  골든크로스 / 200일선 기울기는 사실상 같은 정보 아닌가?) 30개 중
  독립적인 정보는 실제로 몇 개인지 추정하라.
- "항상 켜져 있는 시간이 압도적으로 긴" 지표를 지목하라. 그런 지표는
  구조적으로 유리하거나 불리한가.

[3단계] evaluate.ts의 통계가 정직한가 — 여기가 제일 중요하다
- 적중 판정 창이 바닥 기준 -20 ~ +150거래일이다. 사이클이 40거래일 간격으로
  붙어 있으면 창이 서로 겹친다. 신호 1번이 사이클 여러 개에 동시에 '적중'으로
  기록될 수 있는데, 이때 적중률이 부풀려지는가? 반대로 정확도(precision)는
  Set으로 중복 제거를 하니 같은 신호가 분자에서 한 번만 세어져 낮아지는가?
  이 비대칭이 lift와 p값을 어느 방향으로 왜곡하는지 정량적으로 설명하라.
- p값(binomTailGe)은 "각 신호가 전체 기간에 독립적·균등하게 떨어진다"고
  가정한다. 실제 신호는 뭉쳐서 발생한다(자기상관). 이 가정 위반이 p값을
  낙관적으로 만드는가 비관적으로 만드는가? 더 정직한 대안은 무엇인가
  (블록 부트스트랩, 순열검정 등)? 구체적으로 제안하라.
- 신호를 상태의 상승 엣지(꺼짐→켜짐)로만 정의한다. 바닥 이전에 이미 켜져
  있어서 창 안에 엣지가 없으면 '미적중'이 된다. 이 정의가 장기 추세 지표
  (200일선 위 등)를 부당하게 벌하는가? 어떤 대안 정의가 공정한가?
- 5거래일 클러스터링(EVENT_CLUSTER_DAYS)이 지표마다 다른 영향을 주는가?
- 점수식 score = 적중률×0.4 + min(lift/3,1)×100×0.35 + 남은상승중앙값×0.25
  가 타당한가? 남은상승(captureSharePct)은 미래 고점을 알아야 계산되는데,
  이걸 순위에 넣으면 hindsight bias인가? 세 항의 가중치 근거는?
- 다중검정: 30개를 동시에 검사하는데 Bonferroni나 FDR 보정이 없다.
  23개 사이클 표본에서 적중률 100%가 우연히 나올 확률을 직접 계산하라.

[4단계] regime.ts의 라벨링
- 지그재그가 데이터 시작 경계에서 가짜 사이클을 만드는 걸 막는 로직
  (anchorPeakIdx)이 실제로 모든 경우에 동작하는가? 반례를 만들어 보라.
- 주식 기준 -20%/+25%로 5년간 사이클 23개가 나왔다. 이 임계값이 너무 낮아서
  단순 노이즈를 '상승장'으로 라벨링하고 있는가? 지표 채점 결과에
  어떤 영향을 주는가?
- currentRegime이 '상승'이라고 하면서 지표는 30개 중 2개만 켜져 있는 상황이
  코드상 정상적으로 나올 수 있는 상태인가? 계산으로 보여라.

# 프롬프트 2 — 버그 3개 수정

**첨부할 파일:** `lib/cycle/index.ts`, `lib/cycle/narrative.ts`, `app/cycle/page.tsx`

```
너는 TypeScript/Next.js 개발자다. 첨부한 파일 3개에 확인된 버그 3개가 있다.
아래 지시대로 정확히 고쳐라. 지시하지 않은 것은 건드리지 마라.

## 배경

이 앱은 과거 "상승장 시작점(바닥)"을 라벨링하고, 각 시점에서 30개 기술적
지표 중 몇 개가 켜져 있었는지를 세어 지금과 비교한다.

- lib/cycle/index.ts 의 analyzeCycle() 이 cycleStarts 배열을 만든다.
  각 원소는 { troughDate, measuredDate, on, total } 이고, 바닥으로부터
  CYCLE_START_OFFSET(=30) 거래일 뒤에 몇 개가 켜져 있었는지를 담는다.
- 화면에는 "2026-07-29 → 2/30" 같은 칩이 나열되고, 그 위에
  "과거 상승장 시작 30거래일 뒤에는 평균 13.1개가 켜져 있었습니다"가 뜬다.

## 버그 1 — 평균에 '지금 진행 중인 사이클'이 들어가 있다

lib/cycle/index.ts:103-112 이 모든 사이클에 대해 스냅샷을 만드는데,
여기에는 아직 끝나지 않은 마지막(진행 중) 사이클도 포함된다.

app/cycle/page.tsx:205-208 과 lib/cycle/narrative.ts:77-79 는 이 배열
전체를 평균 낸다. 그 결과 "지금 2/30"을 "과거 평균 13.1개"와 비교하는데
그 평균 안에 지금 값(2)이 들어 있다. 자기 자신과 비교하는 순환 참조다.

실제 데이터: 23개 항목의 합이 301이라 301/23 = 13.09 → "13.1"로 표시된다.
진행 중인 마지막 항목(2)을 빼면 299/22 = 13.59 → "13.6"이 맞다.

## 버그 2 — 마지막 스냅샷은 30거래일 뒤가 아니다

lib/cycle/index.ts:104:

    const idx = Math.min(lastIdx, c.troughIdx + CYCLE_START_OFFSET);

데이터가 모자라면 오늘 날짜로 잘린다. 2026-07-29 바닥에서 오늘까지는 약
22거래일뿐인데, "30거래일 뒤 스냅샷" 목록에 22일짜리가 섞여 들어간다.
이 앱의 지표는 대부분 '확인형'이라 늦게 켜지므로, 미완성 스냅샷은
구조적으로 항상 낮게 나온다. 잘못된 비교다.

## 버그 3 — 분모가 사이클마다 다른데 개수로 비교하고 있다

화면 칩이 "21/23", "7/27", "2/30" 처럼 분모가 제각각이다.
lib/cycle/evaluate.ts 의 onCountAt() 이 그 시점에 아직 워밍업 중인 지표
(365일선, 200주선, 12개월선 등)를 null로 빼기 때문이다.

2021년 사이클은 23개 중에서, 지금은 30개 중에서 센다. 개수를 직접 비교하면
안 되는데 화면은 개수만 보여주고 "평균 13.1개"도 개수로 낸다.

## 고칠 것

### 1) lib/cycle/index.ts

CycleStartSnapshot 타입에 필드 두 개를 추가하라:

    /** 바닥 +30거래일 시점이 데이터 안에 실제로 존재하는가. false면 미완성 스냅샷. */
    complete: boolean;
    /** 켜진 비율(%). 분모가 시점마다 달라서 개수로는 비교할 수 없다. */
    onPct: number;

analyzeCycle() 의 cycleStarts 생성부에서:
- targetIdx = c.troughIdx + CYCLE_START_OFFSET 을 먼저 계산
- complete = targetIdx <= lastIdx
- idx 는 지금처럼 Math.min 으로 클램프 (표시는 계속 하되 미완성 표시를 단다)
- onPct = total > 0 ? (on / total) * 100 : 0

왜 각 필드가 필요한지 한 줄 주석을 달아라. 이 저장소는 주석을 한국어로 쓰고,
"무엇을" 하는지가 아니라 "왜" 그런지를 적는다. 기존 주석 스타일을 따르라.

### 2) lib/cycle/narrative.ts 와 app/cycle/page.tsx — 평균 계산

두 곳 모두 avgAtStart 를 같은 방식으로 고쳐라:

- complete === true 인 스냅샷만 평균에 넣는다
- 개수 평균이 아니라 **비율 평균(onPct)** 을 낸다
- 완성된 스냅샷이 하나도 없으면 null 을 돌려 문장을 생략한다

문구도 바꿔라. 현재:

    과거 상승장 시작 30거래일 뒤에는 평균 13.1개가 켜져 있었습니다.

바꿀 문구(숫자는 계산값으로):

    과거 상승장 시작 30거래일 뒤에는 평균 45%가 켜져 있었습니다 (22번 기준).

괄호 안은 평균에 실제로 들어간 스냅샷 개수다. 지금 값도 비율로 같이 보여줘라.

### 3) app/cycle/page.tsx — 칩 표시

cycleStarts 칩을 "2026-07-29 → 2/30" 에서
"2026-07-29 → 2/30 (7%)" 로 바꾼다.

complete === false 인 칩에는 뒤에 "(진행중)" 을 붙이고 흐리게 처리한다
(기존 Tailwind 클래스 체계를 따를 것 — text-muted 등이 이미 쓰이고 있다).
진행 중 칩은 평균에서 빠졌다는 게 눈으로 보여야 한다.

### 4) (선택) 라벨 문구

app/cycle/page.tsx:551 의 "{report.cycles.length}번을 모두 가리킨 지표" 는
사이클이 늘수록 통과 지표가 급감해서 앱이 고장난 것처럼 보인다.
조건을 명시하도록 "적중률 100% ({report.cycles.length}/{report.cycles.length})"
같은 형태로 바꿔라. 이건 선택 사항이니 판단해서 해도 되고 안 해도 된다.

## 제약

- lib/cycle/evaluate.ts 의 onCountAt() 은 건드리지 마라. null 처리는 의도된 것이다.
- 지표 정의(signals.ts)나 통계 계산(evaluate.ts)은 이 작업 범위가 아니다.
- 기존 타입을 깨지 마라. CycleStartSnapshot 은 API 응답에 실려 나간다.
- 작업 후 반드시 `npm run typecheck` 가 통과해야 한다.

얼마로 바뀌는지도 계산해서 보여줘라.
